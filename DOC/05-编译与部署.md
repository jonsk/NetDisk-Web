# 编译与部署

> 从零到一次完整构建、再到产物嵌入服务端的全流程。前置纪律：**先 `pnpm build`
> 再编译 Go**，否则 embed 的是旧产物（静默错版）。

## 1. 环境要求

| 工具 | 版本 |
|---|---|
| Node.js | ≥ 20（CI 用 22） |
| pnpm | ≥ 9.15.9（建议用 lockfile 精确版本） |
| Go | 服务端（≥ 1.x）—— 用于 embed 产物 |

## 2. 安装依赖

```bash
pnpm install --frozen-lockfile
```

用 `--frozen-lockfile` 保证安装的版本与 `pnpm-lock.yaml` 完全一致（CI 亦如此）。

## 3. 开发

```bash
pnpm dev:admin
```

启动 Vite dev server（端口 **5174**），`/api` 代理到 `http://127.0.0.1:8080`
（由 `vite.config.ts` 的 `server.proxy` 决定，直连本机服务端、与生产同源形态）。

## 4. 生产构建

```bash
pnpm build
```

等价于 `pnpm --filter @netdisk/admin build`（`vite build`），产物输出到
**`apps/admin/dist`**。

关键构建行为（`apps/admin/vite.config.ts`）：

- `base: "/admin/"` —— 资源引用以子路径开头；
- `outDir: "dist"`，`emptyOutDir: true`；
- `target: "es2021"` —— 浏览器下限（兼容较老的企微/钉钉内核 WebView）；
- 生产环境关闭 sourcemap（避免把源码/接口路径打进发布物）；
- 资源文件名带内容哈希（`assets/[name]-[hash].js`）→ 长缓存前提。

## 5. 契约与门禁（构建前建议跑）

```bash
pnpm gen:api       # 修改契约后重新生成类型
pnpm check:api     # 生成物与契约一致性门禁（双向 diff）
pnpm -r typecheck  # 全仓类型检查
pnpm check:rules   # 前端纪律（7 条）
```

CI 会在构建前依次执行 `check:api → typecheck → check:rules`，任何一环失败即红。

## 6. 产物嵌入服务端（关键步骤）

1. 在 `web-com` 下执行 `pnpm build`，得到 `apps/admin/dist`；
2. 将 `apps/admin/dist` 拷贝到服务端 `internal/webui/dist/admin/`（目录名不可变，
   `go:embed` 依赖它）；
3. 再编译 Go 二进制 —— 之后 `/admin` 由服务端 `embed` 提供，与 API 同源。

> ⚠️ 顺序错误（先 go build 再 pnpm build）会导致服务端仍内嵌旧的 admin 产物；
> 发布到生产前务必核验 `/admin/index.html` 是否为新版。

## 7. 部署形态速查

- 单端口：前端与 API 均由 Go 二进制同源提供（Nginx 只做 TLS 与分流，不托管
  静态资源）。
- 子路径：admin 挂在 `/admin/`，SPA 回退由 Go 的 `webui.Handler` 实现，
  无需额外 rewrite。

> 三条"与部署强绑定"的配置（vite `base` / history / `outDir`）及白屏后果详见
> 04-架构设计文档「部署形态」。

## 8. 验证产物

```bash
# 产物可被 embed 的最低校验（与 CI 相同）
test -f apps/admin/dist/index.html || (echo "admin 产物缺失" && exit 1)
```
