# Руководство по чтению кода

> Для разработчика, впервые заходящего в этот репозиторий: знакомство с организацией каталогов, порядком сборки точек входа и распределением обязанностей каждого файла.

## Карта каталогов

```

│     ├─ App.vue          # корневой компонент: провайдеры конфигурации + выход маршрутов
│     ├─ env.d.ts         # типы окружения Vite-клиента
│     ├─ layouts/
│     │  └─ AdminLayout.vue  # sidebar + topbar + выход маршрутов + выход
│     ├─ router/
│     │  └─ index.ts         # таблица маршрутов + охранники before/after
│     ├─ stores/
│     │  └─ auth.ts          # состояние аутентификации: вход/обновление/выход/персистенция токена
│     └─ views/
│        ├─ LoginView.vue    # страница входа
│        ├─ OverviewView.vue # обзор (текущая сессия)
```

## Порядок сборки точки входа (`main.ts`)

Порядок осознанный; при его нарушении «обновление выбрасывает обратно на страницу входа»:

1. `createApp` + `createPinia`, регистрация pinia;
2. `useAuthStore(pinia)` и вызов **`auth.restore()`** (восстановление токена из sessionStorage,
   только чтение локально, без сетевых запросов);
3. `app.use(router)` (охранник читает `auth.ready` / `auth.token`);
4. `app.use(naive)`, `app.mount("#app")`.

> **Почему `restore()` должен быть до `use(router)`**: при первой навигации охранник маршрута, увидев
> «не вошёл» (а токен на самом деле есть), при каждом обновлении выбрасывает пользователя на страницу входа, да ещё с мерцанием.

## Маршруты и охранники (`router/index.ts`)

- `createWebHistory("/admin/")`: должно совпадать с `base: "/admin/"` у Vite;
  при использовании hash-маршрутов вырождается в `/admin/#/users`, что не совпадает с уже реализованным на Go SPA-фолбэком.
- Охранник `beforeEach`:
  - `meta.public` (страница входа) — просто пропустить;
  - нет токена → переход на страницу входа с **сохранением исходного адреса** через `redirect: to.fullPath`;
  - есть токен — пропустить.
- Охранник `afterEach`: по `meta.title` устанавливает `document.title`.
- Маршрут-запас `/:pathMatch(.*)*` перенаправляет на `/overview` (чтобы не было ложного ощущения «система сломана» / белого экрана).

## Store аутентификации (`stores/auth.ts`)

Три ключевые дисциплины (каждая соответствует реальному сбою, см. комментарий в начале файла):

1. явный параметр `audience: "web"`;
2. токен хранится только в `sessionStorage`;
3. при истечении — тихое обновление и повтор, выход только при неудачном обновлении.

`client()` возвращает общий клиент с `getToken` + `onUnauthorized`; `refresh()` намеренно
**не бросает исключение**, а возвращает `string|null`, чтобы клиент решил, «можно ли спасти этот 401».

## REST-клиент (`packages/api/src/index.ts`)

- **Открывает только `request`** (плюс низкоуровневый `send`): обработка ошибок/обновление/заголовки — одна реализация,
  сколько бы ни было интерфейсов.
- Типы **все из контракта** (`schema.gen.ts`); в этом файле больше не пишутся типы с тем же именем, что в контракте.
- `APIError` — единственный бросаемый тип ошибки, распределение по `code`.
- `isBinaryBody`: Blob/FormData/ArrayBuffer отправляются как есть, чтобы поэтапная загрузка не сериализовалась в JSON.

## Скрипты гейтов (`scripts/`)

- `lint-contract.mjs`: гейт контракта — рукописный fetch, рукописный DTO с тем же именем, устаревший артефакт (три точки потери крови).
- `check-frontend-rules.mjs`: 7 дисциплин фронтенда (R1~R7), фиксирует только точки «пишется неверно, ошибки нет, но тихо делается не то».
- `gen-csharp.mjs`: разбор контракта в C#-модели; при отсутствии `desktop/` — только проверка цепочки, выход 0.

> Полные правила каждого гейта, последствия нарушения и вывод прохождения см. в 06-Testovaya-dokumentaciya.

## Рекомендации по чтению

1. Пройдите замкнутый контур аутентификации: `main.ts` → `router` → `stores/auth.ts`;
2. Прочитайте `packages/api/src/index.ts`, чтобы понять запрос/ошибку/обновление;
3. По очереди посмотрите, как `views/` вызывают интерфейсы через `auth.client()`;
4. Если нужно изменить интерфейс: сначала контракт → `pnpm gen:api` → `pnpm check:api`.
